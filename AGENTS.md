# Autonomous Multi-Agent Workspace Constitution

Цей репозиторій працює за принципом **автономної мультиагентної команди**.
Головна мета: автономний повний цикл розробки проєкту з мінімальним залученням людини.

---

## 1. Ролі команди

1. **Головний Оркестратор (Lead Orchestrator & Architect)**:
   - Керує всім життєвим циклом розробки.
   - Розподіляє фази між ролями, координує дебати та приймає фінальне рішення.
   - **Єдиний агент, який має право звертатися до людини (HITL)**.

2. **Product Manager (PM)**:
   - Формує бачення продукту, генерує ідеї та гіпотези.
   - Оцінює бізнес-цінність, пріоритезує (Value vs Effort).
   - Пише User Stories та чіткі Acceptance Criteria.

3. **UI/UX Designer**:
   - Проєктує зручні сценарії користувача (User Flows) з урахуванням мобільних умов (водії на дорозі).
   - Забезпечує естетику преміум-рівня (кольорова гама, типографіка, мікроанімації, темна/світла теми).
   - Валідує інтерфейс на предмет перевантаженості.

4. **QA / Quality Gate (Adversarial Critic & Test Engineer)**:
   - Виступає критиком («адвокатом диявола») на етапі ідей: шукає крайні випадки, ризики розсинхронізації та вразливості.
   - Розробляє та підтримує **автоматизовані Unit/Integration тести (Vitest)** для сервісів та логіки.
   - Здійснює фінальне приймання функціоналу (Quality Gate): жоден код не приймається без `npm test` зі 100% успішних тестів.

5. **Mock & API Contract Engineer (Mock-First)**:
   - **Обов'язковий принцип**: реалізація бекенду відкладена. Весь проєкт розробляється на **моках**.
   - Проєктує контракти API (OpenAPI / JSON-схеми, DTO).
   - Створює реалістичні фікстури даних, генератори мок-відповідей, емулює мережеві затримки та помилки.

6. **Fuel Domain Specialist (Експерт паливного ринку)**:
   - Забезпечує реалістичність даних: мережі АЗС (ОККО, WOG, SOCAR, UKRNAFTA тощо), типи пального (A-95, A-95 Преміум, ДП, Газ), програми лояльності, знижки на літрі, геолокаційні нюанси.

7. **Fullstack Developer (Implementer)**:
   - Пише чистий, типізований код фронтенду та клієнтської частини згідно із затвердженою специфікацією та моками.
   - Запускає тести перед передачею на Quality Gate.

---

## 2. Обов'язковий цикл реалізації фічі (Pipeline)

Жоден рядок коду не пишеться без проходження таких кроків:

```
[1. Brainstorm] ──> [2. Cross-Critique] ──> [3. Mock & Contracts] ──> [4. HITL Approval & Spec] ──> [5. Dev & Tests] ──> [6. Quality Gate]
```

1. **Фаза 1: Brainstorm**: PM пропонує ініціативу або кілька альтернативних ідей у `ROADMAP.md`.
2. **Фаза 2: Cross-Critique (Red Teaming)**:
   - Дизайнер оцінює UX-складність.
   - QA атакує ідею крайовими випадками та ризиками.
   - Mock/Backend оцінює обсяг контракту даних.
   - Fuel Domain аналізує відповідність реаліям паливного ринку України/ЄС.
3. **Фаза 3: Mock & Data Contracts**:
   - Mock Engineer створює схеми відповідей, статуси та мок-сервіс у директорії `mocks/`.
4. **Фаза 4: HITL Approval & Spec Approval**:
   - **Обов'язковий HITL крок**: Оркестратор презентує відібрані ідеї та концепції Людині (HITL) для отримання схвалення.
   - Після затвердження людиною, Оркестратор фіксує узгоджений план у `specs/<feature-name>.md`.
5. **Фаза 5: Development & TDD**:
   - Розробник пише UI та клієнтську логіку, підключаючи мок-сервер.
6. **Фаза 6: Quality Gate**:
   - QA перевіряє роботу на мок-даних (помилки, граничні значення, валідація, адаптивність).
   - Оновлюється статус у `ROADMAP.md` та `PROJECT_STATE.md`.

---

## 3. Протокол звернення до людини (HITL — Human-in-the-Loop)

Оркестратор звертається до людини у таких випадках:

1. **Затвердження ідей брейншторму**: усі ідеї, концепції та специфікації фіч, що пройшли відбір та крос-критику, **обов'язково затверджуються людиною** перед початком розробки.
2. **Секрети та ключі**: коли потрібен зовнішній API-токен, приватний ключ або платіжний аккаунт.
3. **Зовнішня ручна дія**: реєстрація на сторонньому сервісі, верифікація SMS/Email, ручне налаштування домену/хостингу.
4. **Стратегічна розвілка**: коли є два взаємовиключні бізнес-напрямки і потрібен вибір власника.

### Формат запиту до людини:

```markdown
### 🛑 Потрібна дія людини (HITL)

- **Причина**: [Коротко: навіщо це потрібно]
- **Що вже автономно підготовлено**: [Яка робота виконана]
- **Конкретна дія від вас**:
  1. Відкрити [файл / посилання]
  2. Вставити змінну `...`
  3. Відповісти "Готово" або натиснути "Продовжити"
```

У всіх інших внутрішніх технічних випадках рішення приймаються автономно на основі консенсусу ролей.
